## 1. Мета (North Star)

База брендів, за якими система сама стежить на shafa.ua і надсилає в Telegram про кожен новий лістинг:

- фото (одне або кілька);
- назву, бренд, розмір, стан (Новий, Ідеальний, Дуже хороший, Хороший, Задовільний);
- ціну (і стару ціну зі знижкою, якщо є);
- матеріал, якщо відомий;
- пряме посилання.

Вимоги:

- Один товар — одне повідомлення. Без дублів. Перший запуск для нового бренду лише запам'ятовує поточні товари, нічого не надсилає.
- Працює автономно, без мого комп'ютера. Затримка до ~10 хв.
- Бренди й правила додаються без зміни коду (файл `brands.yaml`).
- Правила на бренд: категорії, розміри, мінімальний стан, ціна, матеріали (обов'язкові або виключені), увімкнено/вимкнено.
- Сповіщення про збої та щоденний heartbeat у Telegram.
- Повага до сайту: помірна частота, паузи, звичайний User-Agent, без обходу капчі й блокувань.
- Секрети лише в GitHub Secrets.

## 2. Обов'язкова умова: лише безкоштовні інструменти

- Усе на безкоштовних інструментах. Платне — лише як окрема опція з ціною і **тільки після моєї явної згоди**.
- Дозволено: Telegram Bot API, GitHub (код + стан), GitHub Actions, Cloudflare Workers Free, Google Apps Script, власний комп'ютер, Python/requests.
- Заборонено без згоди: платні проксі й скрейпінг-сервіси (ScraperAPI, Bright Data, Apify…), платні LLM-API для обробки лістингів, платний VPS, платні моніторинги сторінок.
- Якщо безкоштовного не вистачає: спершу оптимізувати (менше запитів, групування, рідше), потім запропонувати найдешевший варіант із ціною і чекати згоди.

### 4.1. Як працює один прохід

1. `brands.yaml` → бренди з однаковими **серверними** фільтрами (розділ, розміри, стан, ціна, матеріал) об'єднуються в одну групу. Одна група = один запит (до 50 брендів).
2. Для кожної групи: 100 найновіших товарів (`orderBy "4"`). Якщо вся сторінка нова, догортаємо до 3 сторінок.
3. Якщо група нова (новий бренд або змінені фільтри) → усі id лише записуються в стан, без сповіщень.
4. Для кожного нового id: локальні фільтри (вік оголошення, слова-виключення, статус) → картка товару (`productDetails`) → фільтр матеріалу (regex по назві + опису + полю «Матеріал») → повідомлення в Telegram.
5. Telegram: до 3 фото альбомом (оригінали `images.shafastatic.net/<id>`) + підпис; якщо фото одне — `sendPhoto` з кнопкою «Відкрити на Shafa»; якщо фото не завантажились — текстом.
6. Невдала відправка → id не позначається баченим, повтор наступного запуску.
7. Стан пишеться в окрему гілку `state` (один коміт, перезаписується щоразу), щоб історія `main` не росла.

Формат підпису (перевірено в dry-run):

```
🆕 Тонкий джемпер із вовни cos розмір l
🏷 COS · розмір L
✨ Стан: Дуже хороший
💰 1 110 грн  ~~1 500 грн~~ (−26%)
🧵 Вовна
🔗 https://shafa.ua/uk/item/...
```

### 4.2. Моніторинг (у коді вже є)

- ⚠️ Алерт у Telegram: 403/429 від Shafa (можливе блокування), група падає 3 рази поспіль, група повертає 0 товарів 12 запусків поспіль, усі запити впали, Telegram не прийняв повідомлення. Повтор того самого алерту не частіше ніж раз на 6 год, після відновлення приходить ✅.
- 💓 Щоденний heartbeat після 9:00 за Києвом: запуски, сповіщення, нові id, запити до Shafa, помилки, найбільша пауза між запусками.
- Якщо heartbeat не прийшов — воркфлоу не запускався (вимкнений, вичерпана квота, збій GitHub).

### 4.3. Команди

```bash
python -m shafa_watch --dry-run          # прохід без Telegram, лише лог
python -m shafa_watch --demo 2           # надіслати 2 найсвіжіші відповідні товари, стан не змінюється
```

## 5. Перевірені факти про Shafa (9.11.2026)

### 5.1. Дані йдуть не з HTML, а з GraphQL

- `curl` сторінки каталогу повертає порожню SPA-оболонку (~10 КБ, 0 товарів). **Парсинг HTML з v1 не працює.**
- Ендпоінти: `POST https://shafa.ua/api/v3/graphiql` (каталог, товар), `/api/v5/graphql` (фільтри), `/api/v3/graphiql-batch`. Клієнт сайту — Apollo.
- Працює **без авторизації й без cookie сесії**, з домашнього IP, ~0,6–0,8 с на запит.
- **Мова:** без cookie `language=uk` назви, описи й стани приходять **автоперекладені російською**. З нею — оригінал українською.
- Заголовки, з якими працює: звичайний браузерний User-Agent, `Content-Type: application/json`, `Origin: https://shafa.ua`, `x-app-platform: web` (необов'язковий).

### 5.2. Запит списку `products`

```graphql
query WEB_CatalogProducts($first: Int!, $pageNum: Int!, $catalogSlug: String, $brands: [Int],
  $orderBy: String, $sizes: [Int!], $conditions: [Int], $priceTo: Int, $priceFrom: Int,
  $characteristics: [Int!]) {
  products(first: $first, pageNum: $pageNum, orderBy: $orderBy, sizes: $sizes, condition: $conditions,
    priceTo: $priceTo, priceFrom: $priceFrom, catalogSlug: $catalogSlug, brands: $brands,
    characteristics: $characteristics) {
    edges { node { id url name thumbnail price oldPrice discountPercent statusTitle condition
                   createdAt isNew catalogSlug brand { id name } sizes { id name } } }
    pageInfo { hasNextPage total }
  }
}
```

- `orderBy: "4"` = за датою додавання (те саме, що `sort=4` в URL).
- `brands` приймає **список** (перевірено до 100 id в одному запиті).
- `sizes` приймає список, і сервер об'єднує їх через **АБО**, зокрема **між різними групами розмірів** (розділ 10.1).
- `first` до 500.
- Без `catalogSlug` і `brands` — увесь сайт (21,3 млн товарів).
- `catalogSlug` — **лише один** на запит.
- У відповіді вже є стан (`condition` 1–5), розміри, ціни, мініатюра, `createdAt`, категорія (`catalogSlug`).
- Інші аргументи, які приймає сайт: `colors`, `priceId`, `ukrainian`, `searchText`, `freeShipping`, `isOnSale`, `cities`.

### 5.3. Картка товару `productDetails`

```graphql
query WEB_ProductDetailsPageProduct($productId: Int!) {
  productDetails(productId: $productId) {
    id name description url price oldPrice discountPercent statusTitle createdAt
    brand { id name } condition { id name } sizes { id name primarySizeName secondarySizeName }
    colors { id name } photos { idStr thumbnailUrl originalUrl }
    characteristics { id title choices { id title } } category { id name } seller { id username }
  }
}
```

- Фото: мініатюра `https://image-thumbs.shafastatic.net/<id>_310_430` (~12 КБ), оригінал `https://images.shafastatic.net/<id>` (~28 КБ JPEG). Обидва публічні.

### 5.5. Інші пастки

- `sort=4` не строго за `createdAt`: ≈15 % верху стрічки — «підняті» старі оголошення. У коді є `max_age_hours` (за замовчуванням 72), яке їх відсіює.
- Новіші товари не завжди мають більший id → дедуплікація лише через множину бачених id.
- «ба**вовн**а» містить «вовн». Regex для вовни: `(?<!ба)вовн`.
- Рекламні картки (`#from-adv`) були проблемою лише для HTML-парсингу. У GraphQL `products` їх немає (реклама йде окремим запитом `topProductsV2`).

### 5.6. Нативна «Підписатися на пошук»

- Мутація сайту `SavedSearchSubscribeld` зберігає: розділ, ціну від/до, стани, **бренди (список), розміри, кольори, характеристики (матеріал)**, текст, «Зроблено в Україні», безкоштовну доставку, знижку.
- Нові речі видно в акаунті: `/uk/my/subscribed-saved-search`. Сповіщення — у застосунку Shafa.
- Не покриває: Telegram, regex по опису, різні правила на бренд в одній підписці, heartbeat.
- **Не міряно:** затримку пушів і ліміт кількості підписок (потрібен вхід у мій акаунт у браузері Claude).

## 7. Архітектура: C (GraphQL) з групуванням

- **A** (запит на кожен бренд) — зайве, бо API приймає список брендів.
- **B** (загальна стрічка новинок + локальний фільтр) — 1,4 тис./год уночі, кілька тисяч удень. Довелося б тягнути 500–1000 товарів кожні 10 хв і відкидати 99,9 %. Ризик пропусків на піку.
- **C** — ✅ обрано. Бренди з однаковими серверними фільтрами → один запит. 1–3 запити за прохід + 1 запит картки на кожен новий відповідний товар.
- **D** (гібрид) — не потрібен.

Навантаження: ≈144 проходи/добу × 2–3 запити ≈ 300–450 запитів на добу + картки. Менше, ніж одна людина, що гортає сайт годину.

Практична межа для приватного варіанта: прохід має вкладатися в ~1 хв, тобто ≈15–20 запитів (пауза 1,5 с) плюс картки нових товарів. Це ≈15 **різних наборів серверних фільтрів**; брендів у кожному наборі — до 50 (і більше пачками).

## 10. Наступна версія: профіль розмірів + категорії на бренд

### 10.1. Що перевірено

- Розміри одягу, штанів і взуття мають **різні id** (розділ 5.4), тож «L», «W32» і «43» не плутаються.
- **Змішаний запит працює:** `sizes: [150, 151, 163, 164, 178]` повертає одяг у L/XL, штани у W32/W33 і взуття 43. Кількість дорівнює сумі окремих запитів (19 866 + 2 301 + 43 950 ≈ 66 117). У видачі немає футболок без L/XL.
- Кожен товар має `catalogSlug` (наприклад `shtany-i-shorty/dzhinsy`), тож категорії можна відсіювати локально, без додаткових запитів.

### 10.2. Дизайн

- Розміри задаються **один раз** (профіль), бо це властивість людини, а не бренду. Запит бренду завжди містить увесь профіль.
- У бренду лише список категорій: людськими словами, їх код переводить у slug-и. Порожній список = усі категорії в моїх розмірах.
- Бренди з однаковим профілем і однаковими серверними фільтрами (стан, ціна, матеріал) далі йдуть одним запитом. Різні категорії **не** розбивають групу, бо фільтруються локально.
- Для винятків (інший розмір взуття, своя ціна на джинси) — `searches` усередині бренду: кілька окремих пошуків, кожен зі своїми полями.
- Дедуплікація спільна: одна річ, знайдена кількома правилами, приходить один раз.

### 10.3. Цільовий формат `brands.yaml`

```yaml
my_sizes:                          # профіль, діє для всіх брендів
  одяг: [L, XL]                    # → 150, 151
  штани: [W32, W33]                # → 163, 164
  взуття: [43]                     # → 178

defaults:
  section: men
  min_condition: 3                 # Новий / Ідеальний / Дуже хороший
  max_age_hours: 72

brands:
  - name: Kapital                  # id підставляє Claude через tools/lookup.py
    categories: [джинси]

  - name: COS
    categories: [джинси, футболки, светри]
    max_price: 2500

  - name: ARKET                    # без categories = усе в моїх розмірах

  - name: Visvim
    searches:                      # винятки: кілька окремих пошуків для одного бренду
      - categories: [взуття]
        sizes: {взуття: [42.5, 43]}
      - categories: [джинси, сорочки]

searches:                          # пошуки за категорією без бренду (опційно)
  - name: Вовняні светри
    categories: [светри]
    materials: [вовна, кашемір]                           # серверний фільтр (поле продавця)
    materials_include: "(?<!ба)вовн|шерст|кашемір|merino|wool|cashmere"
    max_price: 2000
```

### 10.4. Словник категорій (людська назва → slug-и)

| Назва | slug-и |
|---|---|
| джинси | `shtany-i-shorty/dzhinsy` |
| штани | `shtany-i-shorty/bryuki`, `shtany-i-shorty/dzhinsy` |
| шорти | `shtany-i-shorty/shorty` |
| футболки | `futbolki-i-maiki/futbolki`, `futbolki-i-maiki/polo` |
| сорочки | `rubashki/rubashki` |
| светри | `kofti/svitery`, `kofti/dzhempery`, `kofti/pulovery`, `kofti/kardigany` |
| кофти | усе з префіксами `kofti/` і `kofty/` |
| худі/світшоти | `kofti/hudi`, `kofti/svitshoty`, `kofty/tolstovki` |
| верхній одяг | `verkhniaia-odezhda/*` |
| піджаки | `pidzhaki-i-kostiumy/pidzhaki`, `pidzhaki-i-kostiumy/zhakety` |
| взуття | `obuv/*` |
| кросівки | `obuv/krossovki`, `obuv/kedy` |
| черевики | `obuv/botinki`, `obuv/sapogi` |

Словник уточнюється під мій список. Нова категорія = рядок у словнику, без зміни логіки.

### 10.5. Пошук за категорією без бренду

- API це підтримує (`brands` не передається).
- Обсяг (розділ 6): чоловічі светри M/L/XL, стан 1–3 — ≥464 за добу (забагато для Telegram); з матеріалом вовна/кашемір — 64 за добу.
- Два варіанти:
  1. **Серверний фільтр матеріалу**: 1 запит, але ловить лише товари, де продавець заповнив поле «Матеріал».
  2. **Без фільтра матеріалу + regex по назві й опису**: ~470 карток на добу (~3 на 10 хв), менше пропусків, довший прохід.

### 10.6. Що треба змінити в коді

1. `rules.py`: секції `my_sizes`, `searches` (на верхньому рівні й усередині бренду), словники назв розмірів → id і категорій → slug-и; `name` без `id` → підставити id через lookup і записати у файл.
2. `quick_check`: фільтр за `catalogSlug` (точний збіг або `prefix/*`).
3. Групування: ключ групи без категорій; пошук без брендів — окрема група.
4. `query_key`: врахувати профіль розмірів.
5. Тести на живих даних: змішаний профіль, категорії, пошук без брендів, відсутність дублів між правилами.
6. README і `brands.yaml` з прикладами.

## 12. Ризики й обмеження

- **Блокування IP GitHub:** не перевірено. Якщо 403/429 → алерт; варіанти: рідше, більша пауза, домашній комп'ютер, Cloudflare/Apps Script. Обходу (проксі, капчі) не робимо.
- **Зміни API Shafa:** запити скопійовані з клієнта сайту (версія `v2026.11.06.2`). Якщо поле зникне, група почне падати → алерт після 3 збоїв. Лагодити: відкрити сторінку каталогу в браузері, витягти актуальний запит через `window.__APOLLO_CLIENT__.getObservableQueries()`.
- **Запізнення cron GitHub:** 5–30 хв у години пік. Видно в heartbeat («найбільша пауза»).
- **Квота приватного репо:** при частоті 10 хв ≈ 74 %. Не міняти на 5 хв і не міняти раннер на `ubuntu-latest` без перерахунку.
- **Шум:** масові бренди (ZARA, H&M) дають сотні товарів на добу; стримувати розмірами, станом, ціною й категоріями.
- **Умови використання Shafa:** особистий моніторинг з мінімальною частотою, без масового збору.
